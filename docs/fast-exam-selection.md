# PostgreSQL exam issue selection candidate

The new `selectExamCandidates(client,input)` function selects P1 official OX questions in one SQL statement with two bounded source-order index ranges. Default count is 10; caller may request 1–40 using `count`. Duplicates, unpublished rows and rows lacking the current verified active grading key fail closed. Owner + request ID determine a repeatable pivot, while the existing issue-set request lock and idempotent replay remain in the adapter. A materialized upper range fills first; lower wrap range runs only when needed. This removes two sequential DB round trips from the original selector.

P2 derives a case key from the existing `-소문항N` stable-key suffix, selects case groups, and returns **every** subquestion in each chosen group. A group is eligible only when every stored subquestion is published and has a verified active key for the current encryption key ID. The SQL runs as one statement to keep group eligibility and item expansion on one PostgreSQL snapshot. New Docs questions remain unpublished until a verified key is installed.

P2 stable keys without the `-소문항N` suffix are ineligible. The existing approved Docs parser emits that suffix. Inspect any legacy P2 keys lacking it before enabling this selector; never silently treat a stray subquestion as a one-item case. The active-key unique index from migration 0002 prevents multiple active generations; the selection join still deterministically takes the latest verified generation.

Range mode searches the stored prompt/scope text. Weak mode uses the authenticated owner's past incorrect P1 grades or below-max P2 grades. Missing weak history produces no candidates. No Google Sheets or Docs call occurs during issue.

Exact selection uses `mode:'문제지정'` and `specificKeys`. For P1 these are full stable keys and `count` must equal their length. For P2 each key may be a case group key or one subquestion key; subquestion suffixes normalize to the containing case. `caseCount` must equal the number of unique requested groups. Any missing, unpublished or keyless item fails closed; a requested P2 group always expands to all its eligible subquestions.

Additional filters use `questionType` (stored `type`/`detailType`) and optional `year`, `session`, `questionNumber`. P2 year/session/question derive from the verified stable-key grammar. P1 Docs stable keys are arbitrary bracketed IDs; year/session/question cannot safely be inferred from them. P1 uses explicit selection metadata when present, otherwise these exact filters return no candidate. Use full P1 stable key for a known question.

User history modes: `미풀이` (no committed grade), `오답`/`취약` (wrong P1 or below-max P2), `낮은점수` (requires caller-supplied ratio threshold `lowScoreBelow`), `복습대상` (explicit `exam_review_due` row due now), and `원문변경` (prior committed submission used an older problem version). Active PREPARED set items for the same owner are excluded from all selections. `exam_review_due` is introduced by migration 0009 and must be populated by the grading workflow before due mode is exposed; no due dates are invented by selection.

The official exam grading workflow now writes review dates in the same transaction as grade commit: first distinct committed submission +7 days, second +21 days, third and later +60 days. Same-submission replay does not advance the step. A due upsert failure rolls back the grade transaction. The schedule is a question retry aid; it does not assert memory success or alter original answers and scores.

Legacy history backfill uses `db/backfill-exam-review-due.mjs`. Its default is a read-only aggregate inventory. It accepts only committed grade rows with nonblank original answers. P2 zero-point placeholders with no submitted answer are excluded. P1 grade rows lacking an original, missing commit dates, duplicate submission identities, or tied latest timestamps are ambiguous and remain untouched. For a reviewed independent-test-DB run, `--apply --independent-test-db` plus the test-only environment guard inserts **only missing** rows with step `least(attempt_count-1,2)` and `due_at = latest_committed_at + (7/21/60 days by step)`. `ON CONFLICT DO NOTHING` makes replay idempotent. It reports aggregate counts only and never rewrites historical answers or grades. No automatic backfill runs during deployment.

The module is wired into the exam-only PostgreSQL adapter. Disposable PostgreSQL 18 tests passed for P1/P2 selection and complete issue/grade records. Before enabling it on the existing Railway test service: inspect the 9,445-row inventory and multi-subquestion group counts, apply the index migration after review, then measure p50/p95 on actual service. Sheet ordering parity is no longer required.

`benchmarkExamSelection` accepts an already-connected client plus test inputs. It returns only count, p50/p95 and maximum DB-selection milliseconds. It does not log prompts, keys or credentials. End-to-end MCP/AI/network latency must be measured separately; synthetic unit timings are not production latency evidence.

`test/fast-exam-selection.integration.mjs` requires a fresh disposable `exam_selection_*` PostgreSQL database on localhost port 55432. It creates only synthetic questions/keys, asserts actual SQL behavior, and reports DB-selection p50/p95. The integration script does not clear or overwrite a nonempty database and rejects Railway/public hosts.

2026-10-29 isolated PostgreSQL 18 run: 12 synthetic selection samples, p50 2.84 ms and p95 4.68 ms. These are local DB-selection times, not Railway or ChatGPT latency.
